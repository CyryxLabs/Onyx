# Onyx historical Phase 0 audit

Status: **historical snapshot captured on 2026-07-14; superseded for current-state claims by `VERIFICATION_EVIDENCE.md`.** The inventory below is retained as the Phase 0 baseline and intentionally describes what existed at that capture time. It is not an audit of the current development tree, not the authoritative current `VE-SCOPE-M2BB-002`, and not a claim that the complete governed-operations plan is implemented or production-ready.

## 1. Historical audit boundary and method

At capture time, the audit inspected the then-current repository sources, tests, packaging definitions and existing `docs/onyx` architecture/security documents. It preserves the compatibility constitution in `plans/onyx-advanced-entity-redesign.md`: the mission engine, permission broker, dispatcher, memory, credentials, desktop/voice/Orb, dashboard and packaging paths were treated as the stable core. Planned features must extend those contracts through sidecars, registries and adapters rather than replace them.

Status vocabulary is exact:

- `WORKING_AND_VERIFIED`
- `WORKING_WITH_LIMITATIONS`
- `PARTIAL`
- `STUB_OR_MOCK`
- `NOT_IMPLEMENTED`
- `BLOCKED_BY_ACCESS`
- `BLOCKED_BY_LICENSE`
- `BLOCKED_BY_PLATFORM`
- `DEPRECATED`

At the time of this historical capture, the repository `.venv` unit run passed **276 tests**, while dependency consistency, blocking Ruff and compilation checks also passed. Exact current commands, results, limits and input binding are maintained only in `VERIFICATION_EVIDENCE.md`. This baseline does not prove browser, live-provider, physical-device, LAN/mobile or installer operation: its browser attempt was blocked by sandbox `spawn EPERM`, and readiness remained `operationally_verified=false` because Chromium warned, the Gemini credential was absent and live/hardware probes were skipped. The earlier 113-test global-Python run was non-authoritative environment diagnostics only.

## 4. Security posture

Confirmed controls include fail-closed unknown-tool policy, exact approval digests, materialized immutable execution, restricted mission roots, path/symlink/race protections, hash-chained mission/tool audit, secret rejection/redaction, OS-vault credentials, dashboard TLS/pairing/token controls, late-result rejection and explicit uncertain mission outcomes. The authoritative threat register is `docs/onyx/THREAT_MODEL.md`.

Material gaps remain: workspace separation, connector scopes, signed bounded autonomy, centralized kill-switch effects, external idempotency/reconciliation, typed receipts, domain/target allowlists, browser profile isolation, complete DLP/classification and release supply-chain controls. Therefore existing local autonomy must not be interpreted as unrestricted external or cross-workspace authority.

## 5. Dependency and platform truth

- `requirements.txt`, `requirements-dev.txt` and `requirements-build.txt` declare dependencies but are not a reproducible lock. The project `.venv` is internally consistent (`VE-PIP-001`); the global Python import failures only prove that running outside it is incomplete.
- Playwright/browser binaries, Qt Quick 3D, audio/camera/screen facilities and OS automation require environment-specific readiness checks.
- `packaging/onyx.spec` and `scripts/build_release.py` define host-native packages for Windows, macOS and Linux; definitions alone do not prove operational compatibility.
- `docs/onyx/OPEN_SOURCE_AND_API_LICENSE_REVIEW.md` is controlling: proprietary/public distribution remains `BLOCKED_BY_LICENSE`, including unresolved source rights, PyQt/Qt obligations, vendored `dashboard/static/crypto-js.min.js`, SBOM/notices and exact artifact review.
- Official social, ads, executive-office, travel, external-agent and Argos world-intelligence capabilities cannot become working based on code stubs or documentation; they require current access/terms (or, for the proprietary Argos, a built + E6-accepted slice) evidence and a test-account vertical slice.

## 6. Audit conclusion

Onyx is a real local assistant foundation, not yet the complete governed autonomous operations layer. Its strongest proven components are the current identity contract, permission boundary, mission persistence/worker/recovery, verified local mission tools, evidence-shaped step results, local memory/credentials, Orb lifecycle, hardened local data paths and authenticated dashboard primitives. Its broad day-to-day utility tools are real but environment- and verification-limited.

The Phase 4+ operating system described by the master plan remains substantially unimplemented: workspace isolation, typed domain ledgers, bounded grants, Capability Nexus/MCP, provider/model routing, Company Graph, executive connectors, official social/ads/travel integrations, knowledge refinery, unified Command Center and release hardening. The minimum-change path is the target architecture's M0-M5 sequence: freeze current contracts, add an inert sidecar, backfill `legacy-default`, dual-read safely, introduce workspace-aware adapters, replay grants in shadow mode and prove one connector vertical slice. No existing engine, tool or default behavior should be replaced to achieve that progression.
